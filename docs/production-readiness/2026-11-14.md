## Critical blockers

### 1. No verified production deployment

- The Vercel account's linked project list contains no project linked to this repository.
- Repository metadata reports GitHub Pages is not enabled. The previous Pages workflow failed at `actions/configure-pages` with a 404 because no Pages site was configured.
- PR #38 changed Pages deployment to manual-only. Do not publish the static export as a complete app: the Pages workflow removes `app/api`, so chat and task-planning APIs require a separate Next.js-compatible backend.
- Production environment variables and a live application smoke test have not been verified. Never infer that `OPENAI_API_KEY` or `DATABASE_URL` is configured from `.env.example`.

### 2. Authentication and tenant isolation are absent

- No authentication package, login flow, user identity, organization membership, or server-side role model is present in the current application.
- `/api/chat` accepts a client-supplied session UUID. Session and message queries are scoped by that UUID only; there is no authenticated owner check.
- The current database has only `public.a1_sessions` and `public.a1_messages`. Neither table has an owner or tenant key.
- Neon Auth is not enabled on the inspected Neon branches.
- Read-only database inspection found RLS disabled on both tables and no RLS policies.
- The current tables contained zero session rows and zero message rows at inspection time.
- This design is not suitable for multiple businesses, workspaces, staff roles, or confidential seller/customer/property data. Company A must never be able to read or mutate Company B data.

### 3. Incomplete operational security and reliability

- Chat and task-planner rate limits are in-memory per process; they are not shared across serverless instances.
- The calculator tool evaluates expressions using JavaScript `Function`. Replace this with a bounded deterministic parser and edge-case tests.
- The UI describes conversation history as browser-local, while the chat API also persists messages in Neon. Privacy copy, retention, export, and deletion behavior must be reconciled.
- There is no visible unit, integration, RLS, or Playwright E2E test suite. Current CI runs the production build; the security workflow now enforces npm audit at high/critical severity.
- Authentication, audit trails, spend limits, abuse controls, and production observability are not verified.

### 4. Requested business capabilities are not implemented yet

The current repository is a conversational assistant with a task planner and companion UI. It does not yet provide verified end-to-end workflows for:

- Seller Agent / Seller Admin, product catalogue, inventory, quotations, orders, customer and lead management.
- Marketing research, campaign management, attribution, funnel analytics, and results-based marketing advice.
- Customer support tickets, knowledge-grounded support, escalation, and service analytics.
- Accounting, POS, purchasing, sales, returns, receipts, cash/bank ledgers, tax, reconciliation, and profit/loss.
- Real-estate listings, property/land leads, brokerage commissions, deal tracking, and document workflows.
- Multi-business strategy/advisory dashboards or tenant-safe data analysis.

## Prioritized next work

1. **Establish a real production host and environment contract.** Link a verified Next.js-compatible deployment, configure server-side secrets securely, and prove `/api/health` plus chat/task smoke tests. Do not deploy a static-only UI as a complete assistant.
2. **Prototype Neon Auth on a disposable/staging branch.** Verify the SDK, email/password or magic-link configuration, trusted origins, session verification, organization plugin, and local-development flow before touching production.
3. **Implement authentication and multi-tenant authorization.** Add user/organization/membership/role model; derive tenant identity only from verified server-side auth; scope every database query and AI context by tenant.
4. **Add and test RLS.** Include cross-tenant negative tests for reads, writes, updates, deletes, storage, search, and background tasks. Production migration requires a verified backup/restore path and tested staging migration.
5. **Harden the execution core.** Replace dynamic calculator evaluation, add shared rate limiting, request/provider quotas, typed tool schemas, idempotency, audit logs, observability, and safe retry/timeout behavior.
6. **Build the business data model and workflows in phases.** Start with seller/admin CRM and product/inventory/order flows; then POS/accounting; then property brokerage; then marketing research/manager and customer support.
7. **Add automated tests and release evidence.** Unit/integration/API tests, tenant-isolation tests, Playwright critical journeys, accessibility/mobile checks, dependency scanning, and post-deploy smoke tests.

## Release decision

**Do not declare A1 production-ready yet.** The dependency security baseline is improved, but authentication, tenant isolation/RLS, live hosting, production configuration, end-to-end tests, and the requested business workflows remain unverified or absent. Do not assign a readiness percentage until these controls and workflows have measurable acceptance criteria and passing evidence.
